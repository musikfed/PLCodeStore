# PL Code Store — GitHub-first автоматизация, без сервера и без ИИ

Цель: публичная витрина по адресу **https://musikfed.github.io/PLCodeStore/**.
Источники — **только** `vitrine/meta.json` внутри исходных Git-репозиториев.
`view_my_prj` не используется для наполнения новой витрины.

## Где выполняется система

1. GitHub Actions ежедневно запускает `python -m scripts.auto_vitrine`.
2. При первом запуске скрипт инвентаризирует **все доступные репозитории** (до 60 за один запуск, локальный бюджет 350 API-запросов). Далее ежедневно проверяет новые/изменившиеся проекты и проводит полную контрольную проверку раз в 14 дней. Состояние хранится между GitHub Actions запусками в Actions Cache, а не в публичном репозитории.
3. Если внутри проекта нет `vitrine/`, он предлагает отдельный Pull Request с:
   - `vitrine/meta.json` — факты о проекте и версия;
   - `vitrine/generated/cover.svg` — дизайнерская SVG-обложка, не поддельный скриншот.
4. Автор открывает Pull Request в исходном проекте. **Approve / Request changes / Merge** — штатные действия GitHub.
5. Автор поправляет поля `publication: "approved"`, а для закрытого проекта ещё `public_private_approved: true`, когда намерен разрешить показ публичной карточки.
6. После Merge по ежедневному расписанию `python -m scripts.build_pages` собирает только одобренные исходные `vitrine/meta.json`.
7. GitHub Actions разворачивает результат на GitHub Pages. **Нет своего сервера, нет обязательного ИИ.**

В GitHub Pages можно красиво показать карточку и кнопку «❤️ Открыть PR для одобрения», но сам статический сайт не может записывать изменения в Git без дополнительной аутентификации. Поэтому фактическое решение автор принимает в GitHub Pull Request. Review Studio на сайте в данный момент — демонстрационный интерфейс, а не авторизованный инструмент записи.

## Где хранить токен (один, не в JavaScript)

Создай **один** Actions secret в репозитории PLCodeStore:
`Settings → Secrets and variables → Actions → New repository secret`.

Имя: `PL_CODESTORE_TOKEN`. Значение: собственный GitHub PAT с правами на выбранные репозитории. Для создания предложений внутри проектов нужны `Contents: Read and write` и `Pull requests: Read and write`. Для закрытых репозиториев дай этому же токену доступ к ним. Сам токен не передавай в чат и не вставляй в HTML, JSON, README или исходники.

**Работа без токена:** только ограниченное чтение общедоступных проектов. Кросс-репозиторные PR и закрытые проекты недоступны, поскольку встроенный `GITHUB_TOKEN` GitHub Actions ограничен текущим репозиторием.

## Настройка Pages

1. Проверь PR #1 в PLCodeStore и объедини в `main`.
2. Открой `Settings → Pages → Build and deployment → GitHub Actions`.
3. Открой вкладку Actions и запусти `Discover and propose vitrine metadata` вручную, или подожди ночного запуска.
4. В исходных репозиториях смотри вкладку **Pull requests** и принимай предложения. Не забудь установить `publication`.
5. Запусти `Build and deploy PL Code Store Pages` или дождись ежедневной сборки.

## Работа с закрытыми проектами

- Закрытость кода **не ухудшает дизайн** карточки.
- Из `vitrine/meta.json` после одобрения публикуются только выбранные отображаемые данные: имя, описание, версия, направление, статус.
- Публичная обложка **заново создаётся в Actions** из одобренных полей; приватные изображения и ссылки на GitHub-исходники не копируются.
- Кнопки «Исходный код» нет; можно показывать статус и графическую презентацию.
- До явного утверждения `publication: approved` и `public_private_approved: true` закрытого проекта нет в публичном каталоге.

## Если нет веб-интерфейса

- Существующие настоящие изображения в публичных проектах приоритетнее автоматически нарисованной обложки.
- Если веб-интерфейса нет, используется информационная дизайнерская SVG-обложка.
- Если репозиторий пустой, в черновике ставится `В разработке`.
- Не рисуем выдуманный GUI, выдавая его за настоящий.

## Бюджет запросов и минимальная нагрузка

- Первый обход — **все доступные репозитории (до 60)**; затем только новые/изменённые, непроверенные предложения и контрольная проверка через 14 дней.
- Новый лимит **6 PR за запуск** независимо от числа прочитанных репозиториев. Остальные PR формируются следующими ежедневными проверками.
- Локальный бюджет скрипта обнаружения — **350 API-запросов** на запуск; это *внутренний* ограничитель, а не общий лимит GitHub.
- Pages собирается отдельно раз в день; её бюджет не равен лимиту обнаружения.
- Отставание карточек на день допустимо и предусмотрено.
- Если прошлый результат ещё не проверен, повторное открытие того же PR не выполняется.

## Планируемые следующие версии

- Очередь ожидающих решений на .github.io с переходами напрямую к соответствующим PR (только публичным).
- GitLab CI и Forgejo Actions с тем же контрактом vitrine/.
- Реальные схемы работы по подтверждённым компонентам, а не только художественные обложки.
- Доказанный выпуск на все выбранные репозитории и полноценная миграция без нарушения существующего портфолио.

## Как запустить выборку вручную — куда нажимать

1. Сначала объединить [PR #1](https://github.com/musikfed/PLCodeStore/pull/1) с веткой **main** после просмотра изменений. Пока PR открыт, новый workflow отсутствует в меню Actions основной ветки.
2. Добавить один секрет [PL_CODESTORE_TOKEN](https://github.com/musikfed/PLCodeStore/settings/secrets/actions) в **Settings → Secrets and variables → Actions**. Токен не вставлять в чат или файлы.
3. Открыть [Actions → Discover and propose vitrine metadata](https://github.com/musikfed/PLCodeStore/actions/workflows/discover.yml).
4. Справа нажать **Run workflow**, выбрать `main`. Для повторной полной выборки включить **full_scan**; для простого просмотра без создания PR выключить **propose_prs**. Нажать зелёную кнопку **Run workflow**.
5. По завершении открыть созданные [Pull Requests](https://github.com/pulls) в отдельных репозиториях и проверить `vitrine/meta.json` и обложку.
6. После одобрения запустить [Actions → Build and deploy PL Code Store Pages](https://github.com/musikfed/PLCodeStore/actions/workflows/pages.yml).

Первая выборка проводится автоматически по всем доступным проектам без переключателя `full_scan`, если кэш пуст. Для повторной принудительной инвентаризации включай `full_scan`.
